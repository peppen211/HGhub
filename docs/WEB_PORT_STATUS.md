# Web 版本可行性檢查

> 本文件記錄 `web-port` 分支的網頁化檢查。這不是已完成的網頁版，也不代表已部署。

## 目前結論

本專案已有 React 19 + Vite 7 前端，首頁、搜尋、分類、個人頁、播放頁等畫面大多已存在。畫面本身不是主要障礙；真正的障礙是資料 API 與媒體串流目前由 Tauri/Rust 原生層提供。

因此，單純把 Vite 的 `dist` 放到網站主機，不能得到可用的 HGhub 網頁版。

## 已確認的技術依賴

1. `src/api.ts` 直接匯入 `@tauri-apps/api/core` 的 `invoke()`。一般 Safari 沒有 Tauri runtime，呼叫 `app_boot`、`api_feed`、`api_search`、`api_video`、`api_play` 等命令會失敗。
2. `src-tauri/src/api.rs` 將資料請求交給 Rust 的 `edge()` / `net` 層。這層使用原生 HTTP 客戶端、來源檢查、DNS 檢查、重新導向控制及目前選定的上游線路。它不是一般瀏覽器可直接呼叫的 JavaScript 模組。
3. 進一步檢查 `src-tauri/src/net.rs` 後確認：即使是「訪客 GET」，Rust 也不是直接對 `/api/videos` 發 GET，而是對 `/api/edge/request` 發送 JSON 格式的 POST 信封，內含原始 method/path/body/content_type；並設定 `Accept: application/json`、`Referer`。登入後另加 Authorization 標頭。
4. 因為上述請求使用 JSON POST（登入後還有 Authorization），一般網站跨來源呼叫時會涉及瀏覽器 CORS 預檢 OPTIONS。伺服器必須明確允許網站來源、POST/OPTIONS 及所需標頭，瀏覽器才會交付回應。不能用前端設定或 `no-cors` 模式繞過，因為 opaque response 無法讀取 JSON 資料。
5. `src/api.ts` 的封面與 HLS 播放清單會被改寫成 `hg://localhost` 或 `http://hg.localhost`。這些是 Tauri 自訂協定，不是 Safari 網站可使用的網址。
6. `src-tauri/src/media.rs` 負責封面 AES-128-CBC 解密、HLS 播放清單重寫、分片與金鑰請求。只部署靜態網頁不會包含這些能力。
7. `src/App.tsx`、`src/main.tsx`、播放診斷及設定頁也有 Tauri 專用呼叫。即使首頁畫面能載入，仍須處理初始化、除錯、設定與平台判斷。

## 官方文件確認的額外限制

原作者 README 的「實現要點」明確寫出：
- 封面為 AES-128-CBC 密文，由 Rust 解密後才交給前端顯示。
- HLS 播放清單、分片與金鑰會經自訂協定代理及重寫，目的是處理 WebView 的 CORS 與防盜鏈問題。
- 官方安全文件要求圖片、HLS、分片及其他遠端目標經 Rust 網路安全政策檢查。

這些是原作者對現有架構的明確說明，不是我們已實測 Safari 一定會被拒絕。上游 API 是否允許瀏覽器跨來源存取，目前仍沒有可靠證據；不能把「未知」當成「允許」。依照目前讀到的請求格式，直接瀏覽器存取至少需要上游明確支援 OPTIONS 預檢及相應 CORS 標頭。尚未對上游進行高頻或批量探測，也不會用第三方 CORS 代理來猜測結果。

## 抗上游變動設計（已納入後續實作要求）

目標不是承諾「上游改版也永遠不會壞」，而是把變動隔離在單一邊界，讓一般上游格式變更不必牽動整個 UI。這一層只在確認上游允許的存取方式後才能實作，不得用它繞過 CORS、防盜鏈或存取控制。

### A. 固定前端資料契約

網頁元件只依賴專案內部定義的資料型別，不直接讀取上游 JSON 欄位。例如 Feed 頁面只接收統一的 `VideoSummary`，不需要知道上游欄位叫 `video_id`、`id` 或其他名稱。

建議資料邊界：
- `WebApiClient`：只負責呼叫已獲允許的資料來源。
- `normalize`：把上游回應轉成專案內部型別。
- `schema validation`：檢查必要欄位、型別及合理範圍。
- UI：只使用通過驗證的內部型別。

### B. 明確版本與功能能力

- 在單一位置記錄網頁 adapter 的版本及支援功能。
- 啟動時只讀取必要的少量狀態；不為了健康檢查而頻繁輪詢上游。
- 將「資料瀏覽、搜尋、封面、影片播放、登入互動」分別標記為可用、不可用或未驗證。
- 上游回傳未知格式時，安全地顯示暫時無法載入，不猜測欄位、不顯示錯誤內容。

### C. 相容性測試

- 為正常回應、空資料、缺少選填欄位、未知欄位、錯誤狀態及格式改變建立測試樣本。
- 對 normalize/schema 寫單元測試；上游格式變更時，測試應指出是哪個資料欄位不相容。
- 測試樣本只使用合法取得且可保存的非敏感資料；不保存 token、個資、簽名 URL 或媒體金鑰。
- 不以大量真實上游請求當測試；一般 CI 優先使用本地固定測試樣本。

### D. 故障保護

- 對短暫網路錯誤採有限次數、有限等待的重試；不得無限重試。
- 遇到 401/403、CORS、格式不符或上游拒絕時，不反覆重試，也不嘗試偽裝或改走未授權來源。
- 以短暫熔斷避免故障時持續打上游；由使用者手動重新整理或等待冷卻時間後再試。
- 僅在授權允許且內容適合時快取一般非敏感資料；快取須有期限，不能把過期內容偽裝成即時資料。
- 顯示清楚的故障類型，例如「上游暫時無回應」、「上游資料格式改變」、「此功能目前不支援」，不要只顯示空白畫面。

### E. 低負載健康檢查

- 不做高頻背景輪詢、不做批量端點掃描、不並行轟炸上游。
- 優先使用使用者實際操作時產生的請求來判斷健康狀態。
- 如日後確有健康檢查需要，必須先確認上游允許，並設低頻率、單次請求、逾時與熔斷；預設不啟用。
- 健康檢查只能判斷可連線與回應格式，不代表上游授權或未來穩定性。

### F. 上游防護改變的處理原則

若上游新增驗證、改變授權、封鎖客戶端或撤銷存取：
1. 停止相關功能請求並呈現原因。
2. 查找原作者／上游公開且允許使用的新介面或官方說明。
3. 若沒有被允許的存取途徑，保留可用的靜態 UI，暫停資料或播放功能。
4. 不逆向破解簽名、不偽裝官方客戶端、不使用第三方代理規避限制。

### G. 實作順序

1. 先完成上游存取方式與授權確認。
2. 定義內部資料型別與 adapter 介面，不先接真實上游。
3. 以固定測試樣本完成 normalize、schema 與故障測試。
4. 確認資料來源允許後才接上游。
5. 獨立評估封面及 HLS，不能把 API 可用視為影片也可用。
6. 在 iPhone Safari 驗證訪客流程與錯誤處理。
7. 最後才評估部署。

以上設計可以降低「上游欄位或回應格式小幅變動」造成的連鎖故障，但無法消除上游停止服務、封鎖存取或改變授權帶來的影響。

```http
Origin: <正式測試網站來源>
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

檢查回應是否明確允許該來源、POST 及 Content-Type。只有預檢通過，才由真正的瀏覽器頁面發送一次最小化訪客唯讀請求，例如信封內的 `GET /api/videos?page=1&size=1`。不測試登入、帳號、寫入或媒體 URL。

### 目前可安全完成與不可完成的界線

可先進行的工作：前端依賴盤點、平台能力清單、型別／正規化測試設計、靜態 UI 相依性分析。

目前不應開始的工作：把資料 API 接上正式上游、重寫媒體取流、公開代理、部署可供外部使用的網站。原因是尚未確認上游允許瀏覽器來源存取，媒體取流也涉及原作者明確要求不要公開傳播的直連與解密方法。

### 工具能力與驗證狀態

- 可用的 GitHub 讀寫能力可以檢視與更新 `web-port` 分支。
- 目前沒有可直接指定任意 HTTP 方法／標頭並回傳原始回應標頭的通用 HTTP 工具，也沒有可對任意正式網站來源執行 Safari 的瀏覽器工作階段。
- 網頁搜尋器無法開啟 `https://huangguoai.com/api/edge/request`。這只代表該檢索工具無法讀取此 endpoint，不代表伺服器回傳任何特定 HTTP 狀態。
- CORS 預檢需要伺服器回應明確允許實際頁面的 Origin、POST 與 Content-Type；一般 GET 或伺服器端請求成功都不能替代瀏覽器測試。參考 MDN CORS 說明。

### 下一步安全閘門

1. 先取得正式測試網域，並確認上游允許該來源。
2. 在該來源用瀏覽器對訪客唯讀 API 做單次 OPTIONS 預檢與單次最小 GET 測試。
3. 預檢通過後，才建立瀏覽器資料 adapter 與安全樣本測試。
4. 媒體部分另行確認是否有上游正式允許的網頁播放方式；沒有就不實作。
5. 所有測試通過後才評估部署；不自動部署。
