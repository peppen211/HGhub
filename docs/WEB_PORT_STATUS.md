# Web 版本可行性檢查

> 本文件記錄 `web-port` 分支的網頁化檢查。這不是已完成的網頁版，也不代表已部署。

## 目前結論

本專案已有 React 19 + Vite 7 前端，首頁、搜尋、分類、個人頁、播放頁等畫面大多已存在。畫面本身不是主要障礙；真正的障礙是資料 API 與媒體串流目前由 Tauri/Rust 原生層提供。

因此，單純把 Vite 的 `dist` 放到網站主機，不能得到可用的 HGhub 網頁版。

## 已確認的技術依賴

1. `src/api.ts` 直接匯入 `@tauri-apps/api/core` 的 `invoke()`。一般 Safari 沒有 Tauri runtime，呼叫 `app_boot`、`api_feed`、`api_search`、`api_video`、`api_play` 等命令會失敗。
2. `src-tauri/src/api.rs` 將資料請求交給 Rust 的 `edge()` / `net` 層。這層使用原生 HTTP 客戶端、來源檢查、DNS 檢查、重新導向控制及目前選定的上游線路。它不是一般瀏覽器可直接呼叫的 JavaScript 模組。
3. `src/api.ts` 的封面與 HLS 播放清單會被改寫成 `hg://localhost` 或 `http://hg.localhost`。這些是 Tauri 自訂協定，不是 Safari 網站可使用的網址。
4. `src-tauri/src/media.rs` 負責封面解密、HLS 播放清單重寫、分片與金鑰請求。只部署靜態網頁不會包含這些能力。
5. `src/App.tsx`、`src/main.tsx`、播放診斷及設定頁也有 Tauri 專用呼叫。即使首頁畫面能載入，仍須處理初始化、除錯、設定與平台判斷。

## 功能初步分類

### 可優先保留的前端部分

- React 頁面與大部分視覺元件。
- 首頁、搜尋、分類、排行榜、圖文列表等畫面結構。
- 頁面堆疊、分頁、主題與一般互動狀態。
- 已有的訪客使用流程與不登入的產品方向。

### 需要瀏覽器替代方案的部分

- 啟動初始化與資料 API：需要逐項確認上游是否允許一般網站來源直接存取，以及是否有正式支援的 Web API。
- 封面：目前封面走原生解密代理，不能假設瀏覽器能直接顯示。
- 影片播放：HLS 清單、分片、金鑰與防盜鏈處理都依賴原生媒體層，不能只把播放網址塞進 video 標籤。
- 原生設定：線路切換、網路診斷、快取清除、更新檢查及開啟外部連結需要改成適合網站的行為，或在網站版隱藏不適用項目。

### 原版已要求登入的功能

Rust API 對留言送出、按讚、收藏、追蹤等寫入操作會檢查登入 token。網頁版應保留原本這項限制，不應為了「訪客模式」而偽造登入或繞過權限。訪客瀏覽與登入後互動是兩件不同的事。

## 安全與授權界線

- 不修改或覆蓋 `main`，網頁化工作只在 `web-port` 分支進行。
- 保留原有 Tauri 桌面與行動 App 路徑。
- 網站預設維持訪客瀏覽，不新增強制登入。
- 不在前端公開伺服器密鑰或敏感設定。
- 不建立公開、無限制的上游 API／媒體代理，也不提供可被第三方任意轉發的代理端點。
- 不以代理方式繞過上游 CORS、防盜鏈、存取控制或其他限制。
- 不移除原作者版權、商標、授權及使用須知。
- 遵守原專案非商業授權及 README 的使用限制。
- 在瀏覽器資料來源、媒體播放、安全性及授權方式都確認前，不部署、不宣稱可用。

## 下一步

1. 繼續檢查前端啟動流程、訪客初始化與各頁面對原生功能的依賴。
2. 只在不增加上游負載的前提下，確認官方上游是否提供可供瀏覽器使用的 API/CORS 支援。
3. 若上游沒有允許的瀏覽器存取方式，就先停止資料層改寫，不用公開代理或繞過限制的方式硬做。
4. 若資料層可行，再獨立設計封面與影片的合法、受限制處理方式。
5. 完成後才建立瀏覽器 adapter、測試 Safari，最後才考慮部署。
