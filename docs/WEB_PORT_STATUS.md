# Web 版本可行性檢查

> 本文件記錄 `web-port` 分支的網頁化檢查。這不是已完成的網頁版，也不代表已部署。

## 目前結論

本專案已有 React 19 + Vite 7 前端，可執行 `pnpm build` 產生靜態前端資產；但目前不能直接當成完整的一般網站使用。

主要阻礙：

1. `src/api.ts` 透過 `@tauri-apps/api/core` 的 `invoke()` 呼叫 Rust commands。一般 Safari 網頁沒有 Tauri runtime，列表、搜尋、詳情、互動、設定等資料功能無法直接運作。
2. `src/api.ts` 將封面與 HLS 播放列表導向 `hg://localhost` 或 `http://hg.localhost`。這是 Tauri 自訂協定，不是一般網站可用的 URL。
3. `src-tauri/src/media.rs` 負責封面解密、HLS 播放清單改寫與媒體代理。單純部署 Vite 靜態檔案不會包含這些 Rust 能力。
4. Rust 的 `reqwest` 網路層及網路安全政策也不是瀏覽器前端可直接替代的功能。直接改成瀏覽器 fetch 可能遇到 CORS、來源站限制及影片分片請求問題。

## 保留原專案的原則

- 不修改或覆蓋 `main`，網頁化工作只在 `web-port` 分支進行。
- 保留原有 Tauri 桌面與行動 App 路徑。
- 保留既有訪客瀏覽流程，不新增強制登入。
- 不在前端公開任何伺服器密鑰或敏感設定。
- 不建立公開、無限制的上游 API／媒體代理；避免成為共享轉發服務或對上游造成額外負載。
- 不移除原作者版權、商標、授權及使用須知。
- 在網頁功能和安全性未驗證前，不部署、不宣稱可用。

## 下一步技術工作

1. 將 Tauri 呼叫集中在可替換的 runtime adapter，先確保既有 Tauri 版本行為不變。
2. 盤點純瀏覽器可直接完成的功能，以及必須由伺服器承接的功能。
3. 確認上游是否允許瀏覽器來源直接存取；不得以繞過限制的方式處理 CORS。
4. 若需要伺服器端，先設計有存取限制、速率限制、來源驗證及資源上限的私人後端，再評估可行的免費部署方式。
5. 只有在列表、搜尋、訪客模式、封面及播放逐項測試通過後，才考慮正式部署。
